# Harnesses

A harness starts an agent from its file (`factory/agents/<name>/agent.md`) with that agent's tools. The agent files do not depend on any harness. Each harness has a `harness.yaml` that says what it starts, which models an agent's file may declare under it, and what it holds as against what stays instruction; an agent's `harness` and `model` are checked against it by `tools/check_factory.py`. (Until November 2026 these folders were called runners. A runner is now where a job computes: `factory/runners/`.)

- `claude-code/`: Claude Code subagents and skills. Rendered files, a per-call check, a fresh context for each role, each role's record in its own place. Its README says what it is built to enforce and what stays instruction. It has not been exercised against Claude Code.
- `github/`: starts no agent. It is the harness for the two acts by people: a workflow template, the required check on a pull request that carries a lock request or a signature request, the job that records the merge in the study log, a code owners template and a checklist. Its scripts test themselves on a throwaway repository and on payloads in the platform's shapes; the workflow has never run on GitHub.
- `by-hand/`: one command, one write or one read at a time, checked against the role file with the same decision, with no assistant started and so no fresh context. For a person, or for one assistant playing the roles in turn, and for seeing what a role file allows.

A third way has been used once and is not a harness: a coordinating session started each role as a separate subagent and gave it the path of its role file and a task. That gives fresh contexts and holds a role to its file by instruction only. `examples/baton-rouge/README.md` says what that did and did not show; the record of that run is at the branch `records-2026-11`.
